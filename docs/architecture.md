# Event Share 設計書

## 1. 全体構成

```
ブラウザ ──HTTP──▶ Cloudflare Worker (workers/app.ts)
                    ├─ CSRF チェック / セキュリティヘッダー / CSP nonce
                    ├─ React Router v8 (SSR + loader/action + middleware)
                    │    ├─ root middleware: Better Auth でセッション取得 → context
                    │    ├─ routes/*        画面（loader で読み取り、action で更新）
                    │    └─ routes/api.*    リソースルート（認証 / AI チャット / 報告）
                    ├─ app/.server/services  ドメインロジック
                    └─ scheduled()           Cron: リマインダー・不要ファイル掃除
                         │
        ┌────────────────┼──────────────────┬──────────────┬──────────────┐
        D1 (Drizzle)     R2 (画像・動画)     Groq API       Rate Limiting   外部サイト（URL取得）
```

- **画面とデータアクセスの分離**: DB・認証・外部通信は `app/.server/` に置き、route の `loader` / `action` / `middleware` からのみ呼び出します。React Router が `.server` モジュールをクライアントバンドルから除外し、誤って参照するとビルドエラーになります。
- **フォームはプログレッシブエンハンスメント**: ログイン・投稿・編集などは `<Form method="post">` + action で実装しており、JavaScript が無効でも動作します。いいね・コメントなどページ遷移が不要な操作は `useFetcher` を使います。
- **時刻**: DB には UTC ミリ秒（`integer timestamp_ms`）で保存し、入力（`datetime-local`）と表示は `APP_TIMEZONE`（既定 Asia/Tokyo）で変換します。SSR とクライアントで表示がずれないよう、常にタイムゾーンを明示して整形します。

## 2. 認証・権限

| 操作 | 未ログイン | ログイン | 投稿者 | 管理者 |
| --- | :-: | :-: | :-: | :-: |
| 一覧・詳細・検索・カレンダー・AI チャット | ✓ | ✓ | ✓ | ✓ |
| 投稿・コメント・いいね・お気に入り・活動報告・報告 | | ✓ | ✓ | ✓ |
| 既存イベントの未設定項目に情報を追加 | | ✓ | ✓ | ✓ |
| イベントの全項目の編集・非公開化 | | | ✓ | ✓ |
| 他人のコメント・活動報告の非表示、統合、ユーザー管理 | | | | ✓ |

- Better Auth（メール＋パスワード）。セッションは D1 の `session` テーブルで管理し、毎リクエストでサーバー側検証（Cookie キャッシュは使わず、失効・利用停止を即時反映）。
- 投稿者 ID は常にセッションから取得し、フォームの値は使いません（なりすまし防止）。
- **学校所属の確認**: `SIGNUP_MODE=domain` と `SCHOOL_EMAIL_DOMAINS=gse.okayama-c.ed.jp` で、このドメイン（およびそのサブドメイン）のメールアドレスだけが登録できます。`user.schoolVerifiedAt` 列を用意しており、将来メール認証（Better Auth の `emailVerification` + メール送信サービス）を導入した際に、確認済みの生徒だけに投稿を許可するなどの制御を追加できます。

## 3. データモデル

```
user ─┬─< session / account          (Better Auth)
      ├─< events (created_by_id)     イベント本体
      ├─< event_contributions >─ events   情報提供・編集・統合の履歴（項目ごとの差分 JSON）
      ├─< event_sources >─ events         情報の出典 URL（公式 / 応募 / 参照）
      ├─< event_likes / event_bookmarks / event_participations >─ events
      ├─< comments >─ events
      ├─< activity_reports >─ events ─< media_assets (R2)
      ├─< reports（通報: event / comment / activity_report / user）
      ├─< notifications, notification_settings
      ├─< user_interests >─ categories
      └─< chat_sessions ─< chat_messages
categories ─< event_categories >─ events
app_settings（重複判定の配点・閾値など）
```

- **イベント本体と情報提供者の分離**: `events` はイベントの最新状態のみを持ち、誰が何を追加・変更したかは `event_contributions` に記録します。同じイベントへの情報提供は新しい行を作らず、1 つのイベントに集約されます。
- **統合**: 管理者が重複イベントを統合すると、統合元は `status=merged` + `merged_into_id` となり（URL は統合先へリダイレクト）、いいね・お気に入り・コメント・活動報告・出典・履歴は統合先へ移動します（D1 バッチ = トランザクション）。
- **集計値**: 人気順の並び替えのため `like_count` などを `events` に非正規化し、変更時に再集計します。
- **インデックス**: `(status, start_at)`、`(status, application_deadline)`、`(status, created_at)`、`(status, like_count)`、正規化 URL など、一覧・並び替え・重複検索に合わせて作成しています。
- **検索**: 学校規模のデータ量を想定し、キーワードは `LIKE`（ワイルドカードはエスケープ）で検索します。日本語の全文検索が必要になった場合は D1 の FTS5（trigram）や Vectorize への置き換えを検討します。

## 4. イベント投稿と重複対策

```
URL 入力 ─▶ SSRF チェック ─▶ robots.txt 確認 ─▶ 取得（2MB / 8秒 / リダイレクト再検証）
        ─▶ 抽出: JSON-LD(schema.org Event) > OGP/meta > 「日時：」「会場：」などの見出し行
        ─▶（AI 有効時）不足項目のみ AI で整理 — 日付は本文に月日が存在する場合のみ、
            場所・主催などは本文に含まれる文字列のみ採用（捏造防止）
        ─▶ フォームに反映（項目ごとに「ページから取得」「本文から抽出・要確認」「AIが推定・要確認」を表示）
        ─▶ 投稿者が確認・修正して送信
        ─▶ 重複候補の検索（下表）→ 候補があれば提示（投稿は禁止しない）
             既存イベントを確認する / 既存イベントに情報を追加する / 別イベントとして投稿する / 入力内容を修正する
```

| 判定項目 | 初期配点 | 計算方法 |
| --- | ---: | --- |
| イベント名 | 40 | NFKC 正規化（全角/半角・記号・空白を除去）後の文字 bigram Dice 係数 |
| 開催日時 | 25 | 同日 100%、1日以内 80%、3日以内 50%、7日以内 30% |
| 主催団体 | 15 | 正規化後の Dice 係数 |
| 開催場所 | 10 | 正規化後の Dice 係数（両方オンラインなら満点） |
| 概要 | 10 | 文字 bigram の Jaccard 係数 |

- 80 点以上「重複の可能性が高い」、55〜79 点「確認が必要」、54 点以下「低い」。
- 公式 URL の一致は加点（初期 15 点）し、低スコアでも候補として表示しますが、URL だけで同一とは判断しません。
- 開催日が 120 日以上離れている、またはタイトル中の西暦が異なる場合は「別の開催回」とみなし、最大でも「確認が必要」未満に抑えます。
- 配点・閾値・加点・日数は `app_settings` に保存され、管理画面（`/admin/settings`）から変更できます。

## 5. AI イベントレコメンド

```
ユーザー発言
  ├─ ルールベース抽出（分野の同義語辞書、作る/学ぶ/競う/発表、オンライン/会場、都道府県、時期、無料、チーム）
  └─（AI 有効時）LLM で JSON 抽出 → Zod 検証、既知のカテゴリのみ・発言に含まれる語のみ採用
        ▼
会話状態（興味・やりたいこと・形式・場所・時期・費用・参加形態）にマージ
        ▼
不足していれば 1 問だけ質問（興味 → やりたいこと）／「探して」等があれば即検索
        ▼
サーバー側で DB 検索: 公開中・未終了・応募受付中（または締切未設定）のイベントのみ
        ▼
ランキング: カテゴリ一致・キーワード一致・やりたいこと一致・形式/場所/無料/チーム・締切間近・人気
            形式・無料・時期はハード条件、興味がある場合は興味に一致しないイベントを除外
        ▼
推薦理由: AI には「イベントの公開情報 + 一致した事実」だけを渡して生成
          → 存在しない ID・日付・金額・締切・URL を含む理由は破棄し、事実ベースの理由に置換
        ▼
イベントカード: 日時・場所・締切・URL は常に DB の値を表示（未登録は「不明（未登録）」）
               理由欄には「AIによる説明・推測を含む場合があります」と明示
```

- 検索結果が 0 件の場合はイベントを推薦せず、条件を広げる提案のみ行います。
- 未ログインでも利用でき（会話状態はブラウザ内のみ）、ログイン時は会話履歴を保存します。興味・関心のプロフィール保存は、ユーザーが「保存する」を押した場合のみ行います。
- AI が使えない（未設定・障害・タイムアウト）場合もルールベースで同じ流れが動作します。

## 6. 通知

- 発生時に作成: 興味のある分野の新着イベント、コメント（投稿者と過去のコメント投稿者へ）、いいね・お気に入り（投稿者へ、同一ユーザーからは 1 回のみ）
- Cron（毎日 09:00 JST）: お気に入りの応募締切 3 日前、お気に入り・参加予定の開催 2 日前。`dedupe_key` の一意制約で重複送信を防止
- 種類ごとに受信設定を変更可能。現状はサイト内通知のみで、メール・Web Push は `notify()` に送信手段を追加することで拡張できます

## 8. 要確認事項（仮で決めた仕様）

運用前に学校側で確認・決定が必要な点です。現状の仮仕様と、変更する場合の箇所を示します。

1. **学校所属の確認方法**: 登録は `@gse.okayama-c.ed.jp` のみです。メールアドレスの所持確認（メール認証）はまだ行っていません。必須にする場合はメール送信サービス（例: Cloudflare Email Service、Resend など）の選定が必要です。
2. **他の生徒による編集範囲**: 荒らし対策のため、投稿者以外は「未設定の項目への追加」と「カテゴリの追加」のみ可能とし、既存の値と異なる情報は履歴に「提案」として記録しています。Wikipedia のように誰でも編集可能にするかは要検討です。
3. **投稿の事前承認**: 現在は投稿後すぐ公開し、報告・管理者による非公開化で対応する方式です。事前承認制にする場合は `events.status` に `pending` を追加します。
4. **プロフィールの既定の公開範囲**: 「ログインユーザーのみ」を既定にしています。
5. **AI モデル**: Groq の `qwen/qwen3.8-27b` を既定にしています（`GROQ_API_KEY`）。モデルは `AI_MODEL`、プロバイダは `AI_PROVIDER`（`groq` / `workers-ai` / `openai` / `none`）で変更できます。
6. **通知手段**: サイト内通知のみ。メール・プッシュ通知の要否。
7. **データ保持期間**: 既読通知は 90 日で削除。チャット履歴・退会時のデータ削除方針は要決定です。
